# تقرير التدقيق الأمني والتشغيلي — 3 أكتوبر 2026

## الخلاصة

نجح بناء الإنتاج وlint، كما نجح اختبار RLS المعاملي الكامل على PostgreSQL محلي مؤقت بعد إضافة محاكاة RLS لجدول Storage. أظهرت القراءة العامة الحية استجابات فارغة للجداول الخاصة التي اختُبرت، ولم تُظهر صفحات العضوية أو الإدارة محتوى عند فتحها دون جلسة. **لا يعني ذلك أن اختباراً كاملاً بحسابات حقيقية قد أُجري، ولا أن وظائف Edge منشورة:** الاستجابات الحية لوظيفتي Edge كانت `404`، كما أن Google غير مفعّل.

## ما اختُبر فعلياً

### محلياً

- `npm ci --no-audit --no-fund` اكتمل.
- `npm run lint` نجح: صفر تحذيرات وأخطاء.
- `GITHUB_PAGES=true npm run build` نجح، بما في ذلك TypeScript، والتصيير المسبق، والتحقق من SEO والأصول. المخرجات: 10 صفحات عامة و13 غلاف SPA داخلياً.
- حُلّل ملفا Edge Function نحوياً باستخدام esbuild؛ هذا **فحص صياغة فقط** وليس تشغيل Deno أو اختباراً تكاملياً.
- شُغّل `supabase/setup.sql` واختبار `supabase/tests/rls_security_smoke.sql` على قاعدة PostgreSQL محلية مؤقتة أُنشئت وحُذفت لهذا الغرض. أنشئت الحسابات الاصطناعية داخل قاعدة الاختبار فقط؛ أعاد السكربت نتيجة نجاح وتراجع عن كامل معاملة الاختبار.
- شمل السكربت عزل الوثائق والطلبات، منع نشر العضو العادي، منع تصعيد الدور، عزل الرسائل، حد الرسائل، منع تغيير حالة التوثيق/المراجعة الذاتية، وبعض انتقالات الإشراف وحفظ سجل التدقيق.
- المحاولة الأولى لاختبار RLS أخفقت لأن محاكي Storage المحلي لم يكن يفعّل RLS تلقائياً مثل Supabase. بعد تهيئة المحاكي كي يفعّل RLS على `storage.objects` نجح الاختبار. الفشل الأول ليس دليلاً على انكشاف حقيقي، والاختبار الناجح لا يثبت تطابق كل امتدادات Supabase المُدارة مع PostgreSQL المحلي.

### فحص الموقع والخدمة الحية (قراءة فقط)

- صفحة الدخول المنشورة عُرضت بالعربية، وظهر نموذجا البريد/كلمة المرور وزر Google؛ لم تظهر أخطاء Console. **ظهور الزر لا يعني عمل OAuth.**
- فُتحت `/feed/` و`/admin/` مباشرة دون تسجيل دخول؛ أعاد التطبيق التوجيه إلى صفحة الدخول.
- حقق Auth settings الحية أن تسجيل البريد مسموح، وتأكيد البريد مطلوب، وGoogle غير مفعّل.
- أُرسلت طلبات GET عامة إلى `profiles`, `user_roles`, `verification_requests`, `messages`, و`verification_cleanup_queue`. أعادت كلها HTTP 200 ومصفوفات فارغة (`[]`). هذا لا يكشف صفوفاً خاصة للزائر؛ وقد تعني المصفوفات الفارغة عدم وجود بيانات ظاهرة حالياً، ولا تثبت عزل صفوف موجودة تجاه مستخدم مسجل.
- أُرسلت فقط طلبات غير مصادق عليها إلى الوظيفتين `delete-account` و`cleanup-verification-files`. أعادت كلتاهما `404`، ما يثبت أن الاسم غير متاح حالياً على endpoint الحي وقت الفحص، ولا يثبت سبب ذلك. لم تُرسل أي عملية حذف مصادق عليها، ولم تُرسل Webhook أو بيانات اختبار.
- لُقّطت الرئيسية في Chromium عند 390×844؛ ظهر التخطيط المحمول بمحتواه العربي ولم تكن الشاشة بيضاء.

## تغييرات أُدخلت في هذا التدقيق

- تحديث `.github/workflows/deploy.yml` إلى `actions/checkout@v7` و`actions/setup-node@v7` و`actions/upload-pages-artifact@v5` و`actions/deploy-pages@v5`. ملفات الإصدارات الرسمية التي فُحصت تشير إلى Node 24، وإجراء Pages artifact مركّب يستخدم `upload-artifact@v7`.
- جعل نموذج تغيير كلمة المرور يتعامل مع رفض الشبكة والاستثناءات، ويعيد ضبط حالة التحميل ويعرض رسالة عربية بدلاً من تعليق الزر.
- التحقق من JSON/المالك/المسار في Edge function الخاصة بالتنظيف، وتقييد المسار إلى مجلد المالك وبنية مسار آمنة، وعدم تسجيل كائنات استثناء قد تحتوي تفاصيل مستخدم.
- إضافة تحقق مبكر من JSON في وظيفة حذف الحساب، وإبقاء الحذف محصوراً في مستخدم الجلسة المؤكدة؛ رسائل السجل عامة لتجنب تسجيل بيانات حساسة.

دُفعت التغييرات في commit `9b9e37e`، ونجح GitHub Actions run [37131798257](https://github.com/proexcellencenetwork-art/mojtama-al-saytara/actions/runs/37131798257) (build ورفع Pages وdeploy). بعده أعادت الرئيسية و`/about/` و`/login/` و`/register/` و`/feed/` و`/admin/` HTTP 200، وحُمّلت حزمة JavaScript ذات البصمة من صفحة الدخول. يعني HTTP 200 للمسار المحمي أن غلاف التطبيق موجود فقط؛ أكّد فحص المتصفح السابق أن الزائر غير المسجل يُعاد إلى صفحة الدخول. هذا تحقق مسارات/تحميل وليس اختبار مصادقة كاملة.

## ما لم يُختبر أو لم يكتمل

1. لم يُنشأ أو يُستخدم أي حساب حقيقي للاختبار؛ لم تُرسل رسائل تأكيد أو استعادة، ولم تُغيّر كلمة مرور.
2. لم يُختبر التسجيل، تأكيد البريد، تسجيل الدخول، تسجيل الخروج، استعادة/تحديث كلمة المرور أو مسار OAuth عبر تدفق مكتمل.
3. لم يُختبر RLS أو Storage بجلسات JWT لحسابين موجودين فعلياً على خدمة الإنتاج؛ وكانت نتائج REST العامة فارغة.
4. لم يُنفّذ إنشاء أول مدير أو استعلام ترقية الأدوار.
5. Google OAuth غير مفعّل في إعداد Supabase عند القراءة.
6. لا تتوافر صلاحيات جلسة Supabase/CLI في بيئة العمل، لذلك لم يُربط المشروع ولم تُنشر وظائف Edge. اسما الوظيفتين يعيدان `404` حالياً. ولا يوجد إثبات على Webhook التنظيف أو `CLEANUP_WEBHOOK_SECRET`.
7. لا يمكن تأكيد وجود متغيرات GitHub Actions أو قراءتها من CLI: `gh variable list` أعاد `403 Resource not accessible by integration`. لم تُطبع أو تُطلب أي قيمة سرية.
8. لم يُرسل اختبار حقيقي للحد اليومي على HTTP/واجهة الإنتاج؛ حد 15 رسالة وحد 40 للأدوار الموثقة اجتازا منطق قاعدة البيانات المحلية في اختبار RLS.
9. لا توجد بيانات Core Web Vitals ميدانية للزوار في هذا التدقيق؛ أرقام Lighthouse السابقة كانت قياس مختبر (انظر تقرير الأداء).

## قبل فتح التسجيل للعامة

- أضف SMTP موثوقاً واختبر دورة البريد بصندوق اختبار تملكه.
- فعّل Google بعد إعداد OAuth في Google Cloud وSupabase، ثم نفّذ تسجيل دخول OAuth فعلياً.
- أنشئ حساب مالك واستخدم إجراء ترقية المدير من SQL Editor بعد التحقق من هوية الحساب.
- انشر الوظيفتين بالأسرار من لوحة Supabase أو CLI في بيئة تملك صلاحيتها، ثم اختبرهما بحساب اختبار. اضبط webhook التنظيف واختبر حذف ملف اصطناعي.
- أعد اختبار `SECURITY_TEST_CHECKLIST.md` بحسابين عاديين وحساب موثق ومشرف/مدير على **مشروع اختبار منفصل**، بما فيه قراءة رسالة/طلب/وثيقة تخص مستخدماً آخر.
- راقب نشر GitHub Actions بعد الدفع أدناه، وافحص صفحات الموقع والأصول بعده.
- راجع سياسة الخصوصية وشروط الاستخدام، واحتياطات البيانات الصحية الحساسة وخطة الإشراف/الحذف.
