# تقرير التدقيق الأمني والتشغيلي — 3 أكتوبر 2026

## القرار التنفيذي: **NO-GO لفتح التسجيل للجمهور الآن**

نُشرت بوابة تأكيد البريد ثم موافقة المدير على قاعدة الإنتاج، وشُددت صلاحيات القراءة العامة، ونُشرت وظائف Edge، كما أن حزمة GitHub Pages الحية مضبوطة على مشروع Supabase الصحيح. لكن قاعدة الإنتاج تحتوي حالياً **صفراً من مستخدمي Auth والملفات الشخصية**؛ لذلك لم يُنفّذ اختبار بريد فعلي أو اختبار عزل صفوف بجلسات JWT مستقلة. كذلك لم يُتحقق من السر البعيد وDatabase Webhook الخاصين بتنظيف الملفات. هذه فجوات تحقق حقيقية، وليست دليلاً على فشل السياسة.

## ما اجتاز الاختبار محلياً

- نجح `npm run build`، بما فيه التصيير المسبق والتحقق من SEO والأصول، ونجح `npm run typecheck` و`npm run lint` دون تحذيرات أو أخطاء.
- طُبق `supabase/setup.sql` في قاعدة PostgreSQL مؤقتة ومعزولة، ثم اجتاز `supabase/tests/account_approval_smoke.sql`: بدأ الحساب الجديد `pending` بدور `member` فقط؛ لم ير الزائر ملفاً pending أو دور المدير؛ بقيت أدوات المدير غير متاحة للحساب المعلق؛ رُفض تعديل الدور/حالة الاعتماد ذاتياً؛ ووصل اعتماد المدير المؤكد إلى سجل التدقيق.
- فحصت النسخة الموسعة كذلك منع EXECUTE المباشر من `authenticated` على مجموعة دوال `SECURITY DEFINER` المخصصة للمحفزات، ومنع دوال المساعدة الداخلية من `anon`. انتهت المعاملة بـ`ROLLBACK` وحُذفت قاعدة الاختبار.
- أعاد Advisor صفر تحذيرات `SECURITY DEFINER` لدور `anon` بعد migration 015. بقيت عشرة تحذيرات للدور `authenticated` لأن بعض الدوال تُستدعى من RLS أو RPC المدير؛ راجعت حراس الهوية/الدور الأساسية في الشيفرة. يظل هذا تنبيهاً يستدعي إعادة المراجعة عند تعديل تلك الدوال، ولا يُعرض بوصفه «صفر تحذيرات أمنية».

الاختبار المحلي محاكاة PostgreSQL/claims، وليس اختباراً لاتصال REST/JWT حي ولا يثبت كل امتدادات Supabase المدارة.

## ما لم يُختبر بعد

1. لم يوجد مستخدم Auth واحد في قاعدة الإنتاج وقت الفحص؛ لذا لم يُرسل بريد تأكيد/استعادة ولم يُنشأ مدير.
2. لم يُختبر انتقال الحساب عبر تسجيل حقيقي، تأكيد البريد، صفحة «قيد المراجعة»، اعتماد المدير، ثم فتح مزايا العضوية بعد تحديث الجلسة.
3. لم يُختبر عزل الرسائل وطلبات التوثيق والوثائق بين مستخدمين مستقلين عبر JWT حي، ولا حد الرسائل عبر HTTP الإنتاجي.
4. لم تُختبر وظيفة حذف الحساب على مستخدم تجريبي، ولم يُختبر Webhook تنظيف مستند اصطناعي. استجابة `401` بلا تفويض اختبار رفض فقط.
5. قراءة إعدادات Auth سابقة أشارت إلى اشتراط تأكيد البريد؛ لا يوجد إثبات على وصول الرسالة أو موثوقية SMTP. Google OAuth مؤجل واختياري حسب متطلبات المالك.
6. لا توجد بيانات Core Web Vitals ميدانية؛ نتيجة 100/100 في [تقرير الأداء](performance-phase2.md) تخص قياس Lighthouse مختبرياً لصفحتين عامتين فقط.

## بوابات الإطلاق المطلوبة

1. أنشئ حساب المالك ببريد يملكه صاحبه، أكّد البريد، ثم عيّن أول مدير باستعلام القسم 7 من [README](../README.md). لا تُرسل كلمة مرور أو JWT.
2. أنشئ حسابي اختبار عاديين ببريدين تملكهما. تحقق من التأكيد ومن بقائهما `pending`، ومن أن الموافقة وحدها تتيح الوصول للعضوية.
3. استخدم جلسات JWT مستقلة لاختبار قراءة الرسائل والطلبات والوثائق، محاولة تغيير الدور والحالة، النشر، والحد اليومي. يجب ألا يرى كل حساب بيانات الآخر.
4. اضبط SMTP موثوقاً واختبر رسائل التأكيد والاستعادة فعلياً.
5. اضبط `CLEANUP_WEBHOOK_SECRET` في Edge Function Secrets وأنشئ Database Webhook لجدول `public.verification_requests` مع header `x-cleanup-secret`؛ اختبره بملف اصطناعي فقط.
6. اختبر `delete-account` على حساب تطوير disposable لا يحتوي بيانات حقيقية.
7. لا يلزم Google لإطلاق مسار البريد؛ أبقه مؤجلاً حتى إعداد Client ID/Secret لدى المالك واختبار OAuth.
