# بروتوكول التعاون بين Codex وChatGPT

**الهدف:** حفظ ذاكرة المشروع، وتفويض أجزاء العمل المناسبة للمراجعة المستقلة، وتقليل فقد السياق وتعارض التعديلات.

## الحقيقة التقنية

لا يوجد في هذا المستودع اتصال جاهز يتيح لـCodex إرسال طلب إلى محادثة ChatGPT الحالية واستلام تنفيذها مباشرة. ملف `AGENTS.md` يوجّه سلوك Codex، لكنه لا ينشئ قناة اتصال أو مراقبة تلقائية. بروتوكول GitHub أدناه هو المسار العملي المشترك، ويحتاج إلى تمرير رابط المهمة من المستخدم. إذا أُضيف لاحقاً خادم MCP/واجهة API مخصصة، فيجب توثيق كلفتها وصلاحياتها وحدودها واختبارها قبل وصف التفويض بأنه آلي.

## متى يستعين Codex بـChatGPT؟

اطلب مراجعة مستقلة عندما يكون العمل متعلقاً بـ:
- مراجعة تصميم معماري أو مسار مستخدم معقد.
- تدقيق الصلاحيات وRLS وAuth أو بناء خطة اختبارات قبول.
- تحليل عميق للأثر والمخاطر أو المقارنة بين حلول.
- استراتيجية وهوية المجتمع أو كتابة محتوى عربي أو SEO قائم على أدلة.
- مهمة متعددة المراحل تحتاج إلى رأي ثانٍ قبل التنفيذ.

لا حاجة للتفويض في تعديل صغير وواضح يستطيع Codex تنفيذه واختباره بأمان.

## مسار التسليم

1. **Codex يقرأ السياق:** `AGENTS.md`، أحدث حالة في `README.md`، والملفات ذات الصلة. لا ينسخ أسراراً إلى Issue.
2. **Codex يصيغ مهمة قابلة للتنفيذ:** افتح GitHub Issue باستخدام قالب `ChatGPT handoff` من القوالب، أو استخدم نموذج القالب الموجود في نهاية هذه الوثيقة. أدرج الهدف، السياق، المسارات، القيود، معيار القبول، والاختبارات المعروفة.
3. **المستخدم يمرر رابط المهمة:** أرسل رابط Issue أو PR في محادثة ChatGPT واطلب صراحةً مراجعتها أو تنفيذ الجزء المحدد. لا يفترض أن ChatGPT سيراقب المستودع في الخلفية.
4. **ChatGPT ينجز الجزء المسند:** يقرأ المصدر المتاح، ويذكر ما لم يستطع التحقق منه، ويفضّل التغيير في فرع وPR منفصل. إذا تعذرت الكتابة أو الاختبارات، يقدم patch/اقتراحاً واضحاً بدلاً من الادعاء بنجاح التنفيذ.
5. **Codex يستلم ويتحقق:** يسحب الفرع أو يراجع الـPR، ويتأكد من عدم وجود تعارض، ثم يشغّل الاختبارات المناسبة. Codex مسؤول عن إثبات نتيجة الاختبارات في بيئة المشروع.
6. **إغلاق الحلقة:** يحدّث Issue/PR بنتيجة التحقق، والملفات المتغيرة، والاختبارات الناجحة والفاشلة، والمخاطر المتبقية. لا تغلق المهمة لمجرد أن النص أو الكود كُتب.

## قواعد منع التعارض

- لا يعمل الوكيلان بالتزامن على الملف نفسه في فرعين غير منسقين. حدّد مالك التنفيذ الحالي في Issue.
- استخدم فروعاً وPRs صغيرة قابلة للمراجعة؛ لا تدمج تغييراً أمنياً أو إطلاقياً قبل الاختبارات.
- لا تضع مفاتيح أو كلمات مرور أو JWT أو أسرار Webhook في Issues أو السجلات.
- أي تغيير في Supabase الحي، أو فتح التسجيل العام، أو الحذف النهائي، أو إعدادات الإنتاج الحساسة يحتاج فحصاً وموافقة صريحة متناسبة مع المخاطر.
- إذا تناقض تقرير سابق مع الحالة الحية أو أحدث commit، فالحالة القابلة للتحقق هي المرجع.
- حافظ على هوية مجتمع السيطرة المهنية كما وردت في `AGENTS.md`، ولا تحوّل الفرضيات التسويقية إلى حقائق.

## قالب رسالة جاهز لـCodex

انسخ هذا عند الحاجة إلى إعداد تسليم إلى ChatGPT:

```text
أنت Codex وتعمل على مجتمع السيطرة المهنية.
اقرأ AGENTS.md وأحدث حالة في README.md قبل صياغة التسليم.

جهّز GitHub Issue بعنوان:
[AI Handoff → ChatGPT] <عنوان محدد>

تضمّن:
1. الهدف المطلوب والنتيجة المتوقعة.
2. ملخص الحالة الحالية والأدلة/الأخطاء الفعلية.
3. الملفات والمسارات ذات الصلة.
4. القيود الأمنية وهوية المجتمع ذات الصلة.
5. معيار قبول قابل للتحقق.
6. الاختبارات التي شُغّلت فعلاً ونتائجها، مع فصل ما لم يُختبر.
7. الجزء المطلوب من ChatGPT تحديداً، وما ستحتفظ أنت بمسؤوليته بعد رجوع النتيجة.

لا تدّعِ أنك أرسلت المهمة تلقائياً إلى جلسة ChatGPT الحالية. أعطني رابط الـIssue كي أشاركه هناك.
لا تضع أسراراً أو بيانات مستخدمين خاصة في Issue.
```

## رسالة جاهزة للمستخدم بعد إنهاء المهمة

```text

المطلوب منه: <النطاق المحدد>
سأنتظر رجوع المراجعة عبر الرابط الذي تشاركه معه، ثم سأطبق ما يلزم وأشغّل: <أوامر الاختبار>.
الحالة الحالية: <منجز / بانتظار المراجعة / متوقف بسبب مانع واضح>.
```
